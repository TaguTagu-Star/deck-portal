# デッキ構築補佐ポータル 実装計画書（最終版）

作成日：2026-09-13
ステータス：**承認待ち・実装未着手**

---

## 1. 仕様サマリー

### 1.1 目的
- カードゲーム初心者が、カードの役割を理解しながらデッキを作れるようにする。
- 実カードを使わずネット上でデッキ構築を行い、スキマ時間で検討できるようにする。
- 構築したデッキをURL・画像で共有し、レシピを一目で分かるようにする。
- ゲームルールのチュートリアル要素は対象外（ユーザーはルール理解済み前提）。デッキ構築ルール違反時はエラーとして理由を表示する。

### 1.2 対象ユーザー
初心者 / 復帰プレイヤー / 大会向けにデッキを調整するユーザー

### 1.3 MVP成功条件
- 5分以内に最初のデッキを作成できる
- カード検索からデッキ追加まで3操作以内
- デッキ共有URLをログインなしで閲覧できる

### 1.4 対象ゲーム
初期投入データは『鳴潮：対決』1ゲームのみ。ただし`game_id`を採用し、将来のマルチゲーム対応に備えたデータモデルとする。

### 1.5 MVPスコープ（優先度1）
カード検索／カード詳細／デッキ作成／デッキ共有（URL・画像・公開非公開）／認証（メールのみ）／管理機能／レスポンシブ対応。

デッキ分析（枚数・コスト分布・属性分布・種類分布）は優先度2。ただし「メインデッキ属性分布」「サブデッキカード種類」の簡易分析はデッキ確認ダイアログの一部としてMVPに含む。

### 1.6 将来スコープ（本計画の対象外）
AIデッキ提案、対戦結果自動最適化、大会メタ分析、カード価格比較、コメント、フォロー/ランキング、複数ゲーム対応（実運用）、モバイルアプリ、リアルタイム対戦、お気に入り機能、公開デッキ検索、Google/Discord OAuth、OGP対応。

## 2. 用語・対応関係の定義

| UI上の呼称 | 対応する実体 | 備考 |
|---|---|---|
| メインデッキ（main） | アクションデッキ | 合計ちょうど40枚 |
| サブデッキ（sub） | キャラデッキ | 合計3〜15枚 |
| 属性選択リスト（main表示時） | アクションカードの色（赤・青・緑） | 総合ルール301章 |
| 速度範囲（main表示時） | アクションカードのスピード数値範囲フィルタ | 総合ルール307章 |
| 攻撃範囲（main表示時） | アクションカードのダメージ数値範囲フィルタ | 総合ルール308章 |
| 属性タグ／武器種タグ（sub表示時） | キャラカードのタグ（アイコン表示） | 総合ルール204章 |

### 3.1 タグのアイコン対応（総合ルール204.3準拠、固定マスタ）

**属性タグ（`attribute_tag`）**：回折／消滅／気動／電導／焦熱／凝縮（6種）
**武器種タグ（`weapon_tag`）**：長刃／迅刀／拳銃／手甲／増幅器（5種）

アイコン画像はカードレコードにURLを持たせず、タグのコード値からクライアント側で静的アセット（`public/icons/tags/{code}.svg`）にマッピングする。

## 4. デッキ構築ルール（総合ルール101章）

### 4.1 キャラデッキ（sub、3〜15枚）
| # | ルール |
|---|---|
| R-C1 | キャラカードのみ格納可能 |
| R-C2 | 同名カードは同じ種類として扱い、ちょうど3種類のキャラを含む |
| R-C3 | 含めた各キャラについて、そのキャラのLv.0カードをちょうど1枚含む |
| R-C4 | デッキ合計枚数は3枚以上15枚以下 |
| R-C5 | 同じカード番号のカードは1枚まで |

### 4.2 アクションデッキ（main、ちょうど40枚）
| # | ルール |
|---|---|
| R-A1 | アクションカードのみ格納可能 |
| R-A2 | デッキ合計枚数はちょうど40枚 |
| R-A3 | 共通アクションカード、またはキャラデッキ(sub)に存在するキャラの専用アクションカードのみ使用可能 |
| R-A4 | 同じカード番号のカードは3枚まで |

### 4.3 バリデーションの実行方針
- R-C5 / R-A4：カード追加操作の都度、クライアント側で即時チェックし上限超過の追加をブロックする。
- R-C1〜R-C4 / R-A1〜R-A3：デッキ確認ダイアログでの保存時にサーバー側（Server Action）で最終検証し、違反理由をエラー表示エリアに列挙する。
- R-A3はsubデッキの構成に依存する相互参照ルールのため、mainデッキ側の検証時は必ず現在のsubデッキ構成を読み込む。
- 実装は`domain/rules/`に、構造チェック（Zod）とビジネスルールチェック（純粋関数）を分離して置く。各ルールに対し正常系・異常系のユニットテスト（Vitest）を用意する。

## 5. 画面別仕様（確定事項）

### 5.1 デッキ編集画面：検索条件の出し分け

**main（アクションデッキ）選択時**：カード名／収録弾／コスト／速度範囲（スピード）／攻撃範囲（ダメージ）／レアリティ（A1〜A3）／属性選択リスト（色）／条件クリア

**sub（キャラデッキ）選択時**：カード名／収録弾／レベル／属性タグ（アイコン選択）／武器種タグ（アイコン選択）／レアリティ（C1〜C5）／条件クリア

main/sub切替時はフィールド構成ごと出し分け、検索クエリのZodスキーマも`actionCardSearchSchema` / `characterCardSearchSchema`に分離する。

### 5.2 デッキ確認ダイアログ
クライアント状態管理によるモーダルとして実装（ルーティングベースの実装は採用しない）。デッキ保存フローは必ずこのダイアログを経由する。分析エリアには「メインデッキ属性（色）分布」「サブデッキカード種類（タグ）分布」を表示する。

### 5.3 デッキ共有
`visibility`は`public`/`private`の2値。共有ページは未ログインで閲覧可能とし、**カード画像はそのまま表示する（権利リスクは許容し後日対応の方針）**。ただし`image_rights_status`を共有ページの画像表示ロジックが必ず参照する構造にし、将来`restricted`に切り替えたカードを即時非表示にできるようにしておく。デッキ共有画像は、デッキ保存後にデッキ一覧の該当行のボタンから生成・確認できる（画像フォーマットは実装時決定、OGPは将来対応）。

### 5.4 レスポンシブ
カード表示列数：スマートフォン2列、PCは画面幅に応じて最大4列可変。検索エリアはスマートフォン・PC共に折りたたみ可能なアコーディオンUIとする。

### 5.5 認証・管理
ログイン識別子はメールアドレス。認証方式はMVPではメールのみを実装し、Google/Discord OAuthは将来拡張前提の設計にとどめる（実装はしない）。管理者権限は招待制とし、`admin_invitations`テーブル経由でのみ`role=admin`を付与できる。

## 7. API一覧

| 機能 | 種別 | パス／名称 | 概要 | 認証 |
|---|---|---|---|---|
| カード検索 | GET | `/api/cards` | main/subに応じた条件での検索 | 不要 |
| カード詳細 | GET | `/api/cards/:cardId` | 詳細情報取得 | 不要 |
| デッキ一覧取得 | GET | `/api/decks` | ログインユーザーのデッキ一覧 | 必須 |
| デッキ新規作成 | Server Action | `createDeck` | 空デッキ作成 | 必須 |
| デッキ取得 | GET | `/api/decks/:deckId` | 編集画面用データ取得 | 必須（所有者） |
| デッキ保存 | Server Action | `saveDeck` | R-C1〜R-A4の検証を含む保存 | 必須（所有者） |
| デッキ複製 | Server Action | `copyDeck` | コピー作成 | 必須（所有者） |
| デッキ削除 | Server Action | `deleteDeck` | 削除 | 必須（所有者） |
| デッキ公開共有取得 | GET | `/api/decks/:deckId/share` | 未ログイン閲覧可（visibility依存） | 不要 |
| デッキ共有画像生成 | GET | `/api/decks/:deckId/image` | 一覧化画像の生成・返却 | 不要（visibility依存） |
| デッキ分析取得 | GET | `/api/decks/:deckId/analysis` | 属性/種類分布ほか（優先度2詳細版） | 必須（所有者） |
| ユーザー新規登録 | Server Action | `registerUser` | メールでの登録 | 不要 |
| 登録確認・確定 | Server Action | `confirmRegistration` | 確認画面からの本登録 | 不要 |
| ログイン | Server Action | `login` | メール/パスワード認証 | 不要 |
| カード管理（追加/更新） | Server Action | `upsertCard` | 管理者のみ | 必須（role=admin） |
| カード非公開化 | Server Action | `deactivateCard` | `is_active`更新 | 必須（role=admin） |
| 管理者招待 | Server Action | `inviteAdmin` | `admin_invitations`発行 | 必須（role=admin） |

## 8. 実装フェーズ

1. **フェーズ0：基盤整備** — Supabase設定、repository層雛形、Zodスキーマ基盤、CI設定
2. **フェーズ1：認証系** — ログイン／新規登録／登録確認（メールのみ）
3. **フェーズ2：カード検索・詳細** — カードマスタ投入、main/sub出し分け検索API、詳細画面
4. **フェーズ3：デッキ一覧・作成** — 一覧、新規作成、コピー、削除
5. **フェーズ4：デッキ編集・確認** — カード追加/削除、main/sub切替、デッキ確認ダイアログ（R-C1〜R-A4検証含む）、保存
6. **フェーズ5：デッキ共有** — 公開/非公開、未ログイン閲覧、画像一覧化（画像はそのまま表示、`image_rights_status`参照構造）
7. **フェーズ6：デッキ分析（優先度2）** — 枚数・コスト分布等の詳細版
8. **フェーズ7：管理機能** — 招待制の管理者登録・カード追加/更新/非公開化
9. **フェーズ8：レスポンシブ対応・仕上げ** — モバイル2列/PC最大4列、検索エリア折りたたみ、E2E網羅

## 9. 技術的リスク

| リスク | 内容 | 影響 |
|---|---|---|
| 権利未確認カード画像の公開露出 | 共有ページで未ログインの第三者にカード画像が表示される。権利者からの削除要請等に備え、`image_rights_status`を`restricted`にして即時非表示化できる運用フローを整備しておく必要がある | 高（許容済みリスクだが運用整備は必須） |
| RLS設計の複雑化 | `visibility`と未ログイン閲覧を両立するSupabase RLSポリシー設計 | 高 |
| デッキ画像生成の負荷・品質 | サーバーサイド画像生成のコストとレンダリング品質のトレードオフ | 中 |
| 検索パフォーマンス | main/sub別の複数条件検索（コスト・速度・ダメージ範囲、レベル・タグ等）のインデックス設計 | 中 |
| R-A3の相互参照バリデーション | mainデッキの検証がsubデッキの構成に依存するため、保存処理の整合性・排他制御に注意が必要 | 中 |
| 招待制管理者フローの運用設計 | 招待トークンの発行・失効・再送のUI/UX設計が別途必要 | 低〜中 |
